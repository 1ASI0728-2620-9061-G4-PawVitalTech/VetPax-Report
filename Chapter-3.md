## 3.2. User Stories

En esta sección se especifican los requisitos funcionales y no funcionales de VetPax, así como los Epic Stories, User Stories y Technical Stories derivados del proceso de Requirements Elicitation & Analysis.

Los requisitos funcionales establecen las capacidades que debe proporcionar la solución para soportar el seguimiento clínico y nutricional de mascotas geriátricas o con enfermedades crónicas, así como la interacción entre propietarios y profesionales veterinarios.

Por otro lado, los requisitos no funcionales establecen las condiciones de calidad bajo las cuales debe operar la plataforma, considerando principalmente seguridad, disponibilidad, rendimiento, escalabilidad, mantenibilidad e interoperabilidad.

Las User Stories se redactan siguiendo el formato **Como [rol], quiero [necesidad], para [beneficio]**, mientras que sus criterios de aceptación se expresan mediante escenarios verificables utilizando la estructura **Dado – Cuando – Entonces**.

Los requisitos funcionales establecen las capacidades que VetPax debe proporcionar para soportar el seguimiento clínico y nutricional de mascotas geriátricas o con enfermedades crónicas, así como la interacción entre propietarios y profesionales veterinarios.

Para cada requisito se establece una métrica o criterio de cumplimiento verificable que permita comprobar que la funcionalidad esperada ha sido implementada correctamente.

### 3.2.2. Requisitos No Funcionales

Los requisitos no funcionales establecen las condiciones de calidad bajo las cuales debe operar VetPax. Se consideran aspectos relacionados con seguridad, disponibilidad, rendimiento, escalabilidad, mantenibilidad, interoperabilidad, integridad, trazabilidad, usabilidad y compatibilidad.

Cada requisito incluye una métrica cuantificable o un criterio objetivo de verificación que permita evaluar su cumplimiento.

| **ID** | **Título** | **Descripción** | **Métrica / Criterio de cumplimiento** |
|---|---|---|---|
| **RNF-01** | Seguridad de autenticación y autorización | El sistema debe validar la identidad y los permisos del usuario antes de permitir el acceso a recursos protegidos. | El **100% de las solicitudes dirigidas a recursos protegidos** debe pasar por validación de autenticación y autorización. Los accesos no autenticados o no autorizados deben ser rechazados mediante respuestas **401 o 403**, según corresponda. |
| **RNF-02** | Protección de datos en tránsito | La comunicación entre los clientes, backend y servicios externos debe utilizar mecanismos de comunicación cifrada. | El **100% del tráfico externo que transporte información de VetPax** debe utilizar **HTTPS con TLS 1.2 o superior**, o un mecanismo equivalente de comunicación cifrada. |
| **RNF-03** | Disponibilidad | Los servicios principales de VetPax deben permanecer disponibles durante la operación habitual de propietarios y profesionales veterinarios. | El sistema debe mantener una disponibilidad mensual mínima de **99%**, excluyendo periodos de mantenimiento planificado. |
| **RNF-04** | Rendimiento de operaciones frecuentes | Las operaciones habituales de consulta y registro deben responder sin generar retrasos significativos para el usuario. | Al menos el **95% de las solicitudes de consulta y registro** debe completarse en un tiempo menor o igual a **2 segundos** bajo condiciones normales de operación. |
| **RNF-05** | Sincronización en tiempo real | Las actualizaciones clínicas relevantes deben comunicarse oportunamente a los clientes autorizados que se encuentren conectados. | Al menos el **95% de las actualizaciones enviadas en tiempo real** debe reflejarse en los clientes conectados en un tiempo menor o igual a **3 segundos** después de confirmarse el cambio. |
| **RNF-06** | Escalabilidad | El sistema debe permitir incrementar la cantidad de usuarios y solicitudes concurrentes sin modificar la lógica principal del dominio. | En una prueba de carga con al menos **500 usuarios concurrentes**, el **95% de las solicitudes** debe mantener un tiempo de respuesta menor o igual a **3 segundos**. |
| **RNF-07** | Mantenibilidad | La lógica del dominio debe permanecer desacoplada de frameworks, mecanismos de persistencia y proveedores externos. | La sustitución de un proveedor externo que implemente el mismo contrato debe requerir **0 modificaciones en las reglas de negocio del dominio**, limitando los cambios a adaptadores y configuración de infraestructura. |
| **RNF-08** | Interoperabilidad | Los productos digitales de VetPax deben comunicarse con el backend y servicios externos mediante interfaces estandarizadas. | El **100% de los servicios HTTP expuestos para los clientes de VetPax** debe utilizar interfaces RESTful y **JSON** como formato principal de intercambio de información. |
| **RNF-09** | Integridad de información clínica | Las operaciones relacionadas con historial clínico, tratamientos y planes de alimentación deben preservar la consistencia de los datos. | El **100% de las operaciones transaccionales** debe completarse íntegramente o revertirse ante un error, sin dejar información clínica en un estado parcial. |
| **RNF-10** | Trazabilidad de información clínica | Las modificaciones relevantes realizadas sobre la información clínica deben poder asociarse con el usuario y momento en que fueron ejecutadas. | El **100% de los registros y modificaciones clínicas** debe almacenar como mínimo el identificador del usuario responsable y la **fecha y hora** de la operación. |
| **RNF-11** | Usabilidad | Las funcionalidades de uso frecuente deben poder alcanzarse sin una secuencia extensa de navegación. | Las funcionalidades principales de historial clínico, tratamiento, citas y pacientes deben ser accesibles en un máximo de **3 interacciones** desde la pantalla principal posterior a la autenticación. |
| **RNF-12** | Compatibilidad multiplataforma | VetPax debe funcionar mediante una aplicación móvil dirigida a propietarios y una aplicación web dirigida al segmento veterinario. | La aplicación móvil debe funcionar en las versiones de **Android definidas como soportadas por el proyecto**, mientras que la aplicación web debe funcionar correctamente en las **2 versiones estables más recientes de Chrome, Edge y Firefox**. |
| **RNF-13** | Manejo de fallos de servicios externos | La indisponibilidad temporal de un proveedor externo no debe provocar pérdida de información ni comprometer otros módulos de VetPax. | Ante una falla controlada de una integración externa, el sistema debe registrar el incidente, conservar los datos persistidos y evitar que la falla se propague hacia funcionalidades que no dependan del servicio afectado. |
| **RNF-14** | Privacidad de información clínica | La información clínica de una mascota únicamente debe estar disponible para usuarios autorizados sobre el paciente correspondiente. | El **100% de los intentos detectados como no autorizados** para consultar información clínica protegida debe ser rechazado. |

## 3.4. Product Backlog

El Product Backlog de VetPax organiza y prioriza las User Stories y Technical Stories de acuerdo con el valor que aportan al negocio y a los segmentos objetivo. La priorización considera las funcionalidades relacionadas con la Landing Page desde las primeras posiciones, de acuerdo con las disposiciones establecidas para el proyecto.

Posteriormente, se priorizan las funcionalidades que constituyen el núcleo de la propuesta de valor de VetPax, como el seguimiento clínico, los tratamientos, las citas veterinarias, los planes de alimentación y la interacción entre propietarios y profesionales veterinarios. Las funcionalidades de gamificación y determinadas capacidades administrativas se ubican posteriormente debido a que complementan las funciones principales de seguimiento.

Las Technical Stories se incluyen como elementos habilitadores necesarios para implementar las funcionalidades asociadas, pero su posición no se determina únicamente por criterios tecnológicos. Las estimaciones se expresan mediante Story Points utilizando la escala de Fibonacci establecida para el proyecto: **1, 2, 3, 5 y 8**.
